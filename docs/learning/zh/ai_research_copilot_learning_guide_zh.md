# AI Research Copilot 秋招速学指南

这份文档按“你还没有读过项目代码”来写。目标不是让你背每一行源码，而是让你逐步做到三件事：

1. 先用日常语言讲清楚系统在做什么。
2. 再理解每项技术解决了哪个具体问题，而不是只背技术名词。
3. 最后能顺着一次真实实验找到对应源码、运行记录和质量评估结果。

阅读时遵守一个原则：

> 先理解中文作用，再记英文名称，最后看代码实现。英文名称主要用于读源码、查资料和面试交流，不是理解项目的起点。

文档中的固定写法：

- 第一次出现术语时，使用“中文含义（英文原名）”。
- 后面再次出现时，可能直接使用英文原名，因为源码里就是这样命名的。
- 反引号中的内容，例如 `Researcher`、`evidence`，通常是源码里的类名、字段名或工具名。

推荐学习节奏：先看第 0、1 节建立完整画面，再看第 5 至 8 节理解技术细节，最后用第 9、10 节复盘实验和准备面试。

## 0. 先用人话理解项目

### 0.1 项目到底做什么

这个项目不是普通聊天机器人，也不是“上传私人资料后随便问答”的知识库。它解决的是：

> 当用户提出一个需要查资料、比较多种方案、核对证据的复杂问题时，系统先制定研究计划，再从本地文档和互联网收集证据，最后生成带来源引用的研究报告，并检查报告是否真的得到证据支持。

`AI Research Copilot` 可以翻译为“人工智能研究助手”：

- `AI`：人工智能，这里主要指大语言模型。
- `Research`：研究，不是立即回答，而是先拆问题、找资料、读资料、比较证据。
- `Copilot`：副驾驶或助手，强调系统帮助人完成研究，而不是代替人做最终决策。

整个过程用中文表示如下：

```text
用户提出复杂问题
-> 判断问题是否清楚，并拆成研究任务
-> 决定每个任务需要使用哪些资料和工具
-> 搜索互联网、检索本地文档、读取历史记忆
-> 把找到的内容整理成可引用的证据
-> 根据证据生成研究报告
-> 检查报告是否漏答、缺少引用或脱离证据
-> 保存有价值的记忆和完整运行记录
```

可以把它类比成一个小型研究团队：

| 系统角色 | 中文作用 | 类比 |
| --- | --- | --- |
| `Planner` | 规划器，把大问题拆成小问题 | 研究组长先列提纲 |
| `ResearchSupervisor` | 研究监督器，决定查什么、用什么工具、证据需要多少 | 组长分配调查任务 |
| `Researcher` | 研究执行器，实际搜索和阅读资料 | 研究员查论文、做笔记 |
| `Reporter` | 报告生成器，根据证据组织答案 | 撰写最终报告的人 |
| `Verifier` | 校验器，检查结论和引用 | 审稿人检查证据 |
| `Evaluator` | 评估器，把质量问题变成可检查的指标 | 质量检查表 |

### 0.2 先认识 14 个高频词

下面这些词会反复出现。现在只需要理解作用，不需要记实现细节。

| 术语 | 中文解释 | 在本项目里的作用 |
| --- | --- | --- |
| `Agent` | 智能体，即“让大模型承担一个明确角色并调用工具完成任务” | 规划器、研究执行器、报告生成器都属于不同角色的 Agent |

| `Grounding` | 证据落地或事实依据约束 | 要求报告内容建立在检索到的真实资料上 |

| `Citation` | 引用 | 把报告中的结论指回具体证据和来源 |

| `Trace` | 运行轨迹 | 记录系统每一步做了什么、调用了什么工具、为什么停止 |
| `Evaluation` | 质量评估 | 检查计划覆盖、证据充分性、引用准确性等 |
| `Provider` | 外部能力供应方 | 提供大模型、向量、重排或联网搜索服务，例如 DashScope、Tavily |
| `Artifact` | 运行产物 | 一次实验留下的报告、轨迹和评估 JSON 文件 |
| `API` | 应用程序接口 | 前端或其他程序通过固定地址提交任务、查询状态和读取结果 |
| `JSON` | 结构化文本数据格式 | 保存运行轨迹、质量评估和部分接口结果 |

### 0.3 一句话定位

面试时可以先说：

> 我做了一个面向复杂问题的人工智能研究助手。它不是让大模型直接回答，而是把任务拆成规划、资料检索、证据整理、报告生成、引用校验和质量评估等步骤，最终输出可追溯的引用型研究报告。

等面试官追问技术时，再补充：

> 系统使用 LangGraph 管理研究工作流，使用 RAG 为回答提供本地资料依据，并通过运行轨迹和质量评估解释每次回答为什么可信。它不是简单的“取前几个相似片段后直接回答”。

### 0.4 技术组件地图

下面先回答“这些英文技术到底各自干什么”。同一行里的组件属于同一类职责，不要把它们混在一起背。

| 技术或组件 | 它是什么 | 在本项目里的具体作用 |
| --- | --- | --- |
| `LangGraph` | 大模型工作流编排框架 | 管理规划、研究、报告、校验和修订的节点顺序与状态 |

| `DashScope` | 阿里云模型服务平台 | 提供 Qwen 大语言模型、文本向量模型和重排模型的真实接口 |

> LangGraph 管流程，FastAPI 接请求，Celery 和 Redis 跑后台任务，Qdrant 与 SQLite 找本地资料，DashScope/Qwen 提供模型能力，Tavily 找互联网资料，MCP 统一工具调用方式。

## 1. 面试主讲的核心链路

这个项目要当“大模型应用项目”来讲，不要讲成后台管理系统。`documents`（文档）、`memory`（记忆）、`runs`（运行记录）、`jobs`（后台任务）这些接口的增删查改只是支撑能力，不是亮点。真正该讲的是下面 6 条链路。

### 链路一：复杂问题到研究计划

```text
用户问题
-> 澄清模块判断问题是否明确
-> 规划器把问题拆成多个研究任务
-> 研究监督器决定查询语句、工具和证据要求
```

先解释名词：

- `Clarify`：澄清。如果问题缺少对象、范围或时间条件，先要求补充信息。
- `Plan item`：计划项，即一个可以独立执行的小研究任务。
- `Query rewrite`：查询改写。把用户的口语问题改成更适合搜索引擎或文档库检索的关键词。
- `ConductResearch`：源码中的结构化研究指令，明确“研究什么、用哪些工具、至少需要多少证据”。

核心难点：

- 用户问题往往很宽泛，不能直接丢给模型回答。
- 要把问题拆成可执行的研究子任务。
- 要决定每个子任务使用互联网搜索、本地文档检索、系统记忆还是外部工具。
- 要把模型的决策结构化，不能只拿一段自然语言当计划。

举例：

> 用户问“如何为数据分布不同、设备算力不同的联邦学习系统设计个性化方案”，规划器可以拆成“数据异质性问题”“模型异质性问题”“可选算法比较”“最终工程建议”四个任务，而不是直接让模型写答案。

面试说法：

> 我把大模型从“直接回答者”变成“受控研究流程里的决策者”。规划器负责拆问题，研究监督器输出结构化的 `ConductResearch` 指令，其中包含要使用的工具、互联网和本地查询、最低证据数量、来源多样性以及证据充分条件。

源码锚点：

- `src/agentic_research_copilot/graph_runtime.py`
- `src/agentic_research_copilot/agents/planner.py`
- `src/agentic_research_copilot/agents/supervisor.py`
- `src/agentic_research_copilot/schemas.py`

### 链路二：研究执行与工具选择

```text
结构化研究指令
-> 研究执行器进入有次数上限的循环
-> 思考下一步、联网搜索、调用外部工具或结束研究
-> 收集证据
-> 检查证据是否足够
```

先解释名词：

- `Bounded loop`：有边界循环。研究执行器可以多轮搜索，但有最大次数，不能无限运行。
- `Tool call`：工具调用。大模型只负责决定调用哪个工具，真正的搜索、检索和读取由程序执行。
- `think_tool`：让研究执行器先总结当前证据和缺口，再决定下一步。
- `web_search`：调用联网搜索服务。
- `mcp_tool`：通过 MCP 协议调用已注册工具。
- `ResearchComplete`：研究结束信号，表示证据已经足够或达到迭代上限。
- `Sufficiency check`：充分性检查，判断现有证据能否覆盖研究任务。

核心难点：

- 不能让智能体无限搜索，否则时间和模型调用成本不可控。
- 不能所有任务都启动多个智能体，简单问题应该走简单路径。
- 每一轮搜索和阅读都要记录查询语句、证据数量、来源数量、缺口和停止原因。
- 大语言模型（LLM）返回的结构化数据可能不规范，例如本应是列表的字段返回 `null`。

面试说法：

> 研究执行器不是可以随意行动的智能体，而是一个有次数上限的工具循环。它每轮只能选择思考、联网搜索、调用已注册工具或结束研究，并记录本轮反思、新增证据、来源数量和证据缺口，因此可以复盘为什么继续搜索或停止。

源码锚点：

- `src/agentic_research_copilot/agents/researcher.py`
- `src/agentic_research_copilot/agents/supervisor.py`
- `src/agentic_research_copilot/graph_runtime.py`

### 链路三：外部搜索阅读到可引用证据

```text
联网搜索
-> 搜索服务返回标题、摘要、网址和网页正文
-> 来源阅读器提取与问题相关的内容
-> 生成带来源信息、可被报告引用的证据
```

先解释名词：

- `Snippet`：搜索结果摘要，通常只有一两句话，信息可能不完整。
- `Raw content`：网页原始正文，比摘要完整，但可能很长并包含菜单、广告等噪声。
- `Source reader`：来源阅读器，负责从网页正文中提取与当前问题相关的段落。
- `Extract`：直接提取匹配内容。
- `Model compression`：让模型把长网页压缩成与问题相关的短证据。
- `Chunk-rerank-compress`：先把长网页切成小段，再排序选出最相关片段，最后压缩。
- `Citation-ready evidence`：已保存标题、来源、网址和正文，可直接用于引用的证据对象。

核心难点：

- 搜索结果摘要太短，不足以支撑研究报告。
- 网页原始正文太长、噪声太多，直接交给报告模型会增加成本，也难以控制引用。
- 切分后的文本片段可能把前提和结论分开，导致证据不完整。
- 最终报告不能让模型自己编造来源或网址。

面试说法：

> 外部搜索不是只看搜索摘要。Tavily 搜索服务可以返回网页正文，系统再根据当前问题提取或压缩相关内容，生成带来源信息的证据对象。报告生成器只能引用这些已有证据，避免模型自己编造引用。

源码锚点：

- `src/agentic_research_copilot/search.py`
- `src/agentic_research_copilot/source_reader.py`
- `src/agentic_research_copilot/agents/researcher.py`

### 链路四：本地智能体式 RAG 证据检索

```text
PDF、Markdown、HTML 或纯文本文件
-> 文档读取器保留标题、章节、页码等结构
-> 切成用于检索的小文本片段，并补充片段所属背景
-> 同时进行语义检索和关键词检索
-> 补充轻量实体关系候选
-> 合并多路候选并重新排序
-> 为命中的小片段补回父段落和相邻内容
-> 形成可引用证据
```

先解释名词：

- `Agentic RAG`：智能体式检索增强生成。不是固定检索一次，而是由研究执行器根据任务决定何时检索、检索什么、证据不够时是否继续。
- `DocumentReader`：文档读取器，把 PDF、Markdown、HTML 或纯文本解析成保留结构信息的段落。
- `Metadata`：元数据，即正文之外的描述信息，例如文档标题、章节、页码、来源网址。
- `Chunk`：文本片段。文档太长，不能整体做检索，所以要切成较小片段。
- `Child chunk`：用于精确检索的小片段。
- `Parent context`：小片段所属的较大段落，用于补足上下文。
- `Contextual retrieval prefix`：上下文检索前缀，在小片段前补充文档名、章节等背景，避免片段脱离语境。
- `Dense retrieval`：语义向量检索，寻找“意思相近”的内容。
- `Embedding`：向量表示，把文本转换成一组数字，使程序可以计算语义相似度。
- `BM25`：经典关键词检索算法，擅长匹配论文名、缩写、指标和专有名词。
- `FTS5`：SQLite 自带的全文检索组件，本项目用它保存并执行 BM25 检索。
- `Fusion`：候选融合，把语义检索、关键词检索和图关系检索得到的结果合并。
- `Rerank`：重排，用更精细的模型对候选证据重新打分和排序。
- `Graph signal`：图关系信号，根据实体之间的共现关系补充可能相关的文本片段。
- `Parent/neighbor context expansion`：上下文扩展，命中小片段后补回它的父段落和相邻片段。

核心难点：

- 文档解析阶段如果丢掉标题、页码和段落信息，后面的检索很难补救。
- 只做语义向量检索，并取相似度最高的前几个结果，容易漏掉论文名、方法名、缩写和指标。
- 单个小片段可能缺少前提或结论，需要补回父段落和相邻内容。
- 语义检索、关键词检索、图关系补充和重新排序必须各自解决明确问题，不能只是为了堆技术。

面试说法：

> 我这里的 RAG 不是“输入问题、取前几个片段、直接回答”。文档先被解析成带标题、章节和页码信息的段落，再切成便于精确检索的小片段。检索时，Qdrant 向量数据库负责语义召回，SQLite FTS5/BM25 负责关键词召回，轻量实体关系用于补充候选；合并后再用 Qwen 重排模型排序，最后为命中的小片段补回父段落和相邻上下文，再交给报告模型。

源码锚点：

- `src/agentic_research_copilot/document_reader.py`
- `src/agentic_research_copilot/retrieval/store.py`
- `src/agentic_research_copilot/retrieval/fulltext.py`
- `src/agentic_research_copilot/retrieval/rerank.py`

### 链路五：报告生成、引用校验和质量评估

```text
已收集的证据
-> 报告生成器分章节组织内容
-> 报告中的引用编号映射回具体证据
-> 校验器检查薄弱结论和缺失引用
-> 评估器计算覆盖程度和证据一致性
-> 不合格则修订，合格则结束
```

先解释名词：

- `Citation index`：引用编号，例如报告中的 `[1]`，它必须指向系统已经收集的一条证据。
- `Coverage`：覆盖程度，检查报告是否回答了计划中的各项问题。
- `Faithfulness`：忠实度，检查报告表述是否与所引用证据一致。
- `Proxy`：代理指标。当没有昂贵的人工标注时，用一组可自动计算的规则近似判断质量。
- `Revision`：修订。如果证据或引用检查不通过，回到前面补证据或改报告。

核心难点：

- 大模型生成报告时容易编造引用。
- 有些段落可能没有证据支撑。
- 证据数量够，不代表覆盖了研究计划。
- 需要把失败原因显式记录，而不是只返回“失败”。

面试说法：

> 报告生成器不能自由编写来源，只能基于已有证据生成章节，并通过引用编号映射回证据对象。校验器和评估器会检查引用准确率、来源覆盖、计划覆盖、证据充分性、无证据支持的章节和证据一致性。曾经有一次架构类实验因为证据不足被评估器拦下，这说明质量门控确实参与了运行，而不是只写在文档里。

源码锚点：

- `src/agentic_research_copilot/agents/reporter.py`
- `src/agentic_research_copilot/agents/verifier.py`
- `src/agentic_research_copilot/evaluation.py`
- `examples/resume-demo/*.evaluation.json`

### 链路六：记忆、运行轨迹和可复盘实验

```text
一次研究的结果
-> 筛选并写入系统记忆
-> 按临时记忆、主题总结、稳定事实分层保存
-> 记录每一步运行事件
-> 保存关键步骤的状态快照
-> 沉淀实验报告、轨迹和评估文件
```

先解释名词：

- `Session memory`：会话记忆，只对当前一次会话或研究任务有用。
- `Summary memory`：总结记忆，保存某个主题或项目的阶段性结论。
- `Canonical memory`：规范记忆，保存相对稳定、以后可以复用的事实。
- `Confidence`：置信度，表示系统对一条记忆可靠程度的估计。
- `Conflict governance`：冲突治理，新旧记忆冲突时不直接覆盖，而是标记并等待复核。
- `Checkpoint`：检查点，即工作流运行到关键节点时保存的状态快照。
- `Replay`：回放，根据轨迹和检查点查看一次任务当时如何执行。
- `Demo`：演示实验。本项目中的 demo 不只是现场页面，还包括可重复检查的报告、轨迹和评估文件。

核心难点：

- 系统记忆不能等于把全部聊天历史直接拼进提示词。
- 稳定事实不能被一次输出随便覆盖。
- 面试实验不能只展示最终答案，还要展示中间过程。
- 真实外部服务的延迟、报错和结构化输出异常都要能定位。

面试说法：

> 系统记忆分成会话记忆、主题总结和稳定事实，并带有置信度与冲突处理状态。运行轨迹记录规划、研究、工具调用、质量评估和检查点，因此我可以打开实验产物，复盘一次研究为什么这样执行、用了哪些证据以及在哪里失败过。

源码锚点：

- `src/agentic_research_copilot/memory/store.py`
- `src/agentic_research_copilot/telemetry.py`
- `src/agentic_research_copilot/storage.py`
- `examples/resume-demo/*.trace.json`

## 2. 核心难点总结

面试时如果只讲一个“技术难点”，太薄。这个项目可以讲 5 个核心难点。

### 难点一：如何让大模型从直接回答变成受控研究流程

关键设计：

- LangGraph 把每个步骤定义成明确节点，而不是把所有逻辑塞进一次模型调用。
- 规划器把复杂问题拆成可执行任务。
- 研究监督器用结构化字段输出工具选择和证据要求。
- 研究执行循环设置最大次数，控制时间和调用成本。
- 校验器和评估器负责质量门控，不合格时触发修订或标记失败。

一句话：

> 难点不是调模型接口，而是把模型的自由生成收敛成可检查、可回放、可失败重试的研究流程。

### 难点二：如何让 RAG 不停留在“取相似度最高的前几个片段”

关键设计：

- 文档读取器保留标题、章节和页码等结构信息。
- 上下文检索前缀为小片段补充所属文档和章节背景。
- Qdrant 语义向量检索与 SQLite BM25 关键词检索组成混合检索。
- 轻量实体关系信号补充与查询实体相关的候选片段。
- 重排模型对合并后的候选做最终排序。
- 父段落和相邻片段扩展用于补足完整上下文。

一句话：

> 难点是把“召回一个片段”升级成“召回可用于报告生成的证据上下文”。

### 难点三：如何控制引用和幻觉

关键设计：

- 来源阅读器把网页正文压缩成与问题相关的证据。
- 报告生成器只能引用系统已经收集的证据。
- 报告中的引用编号必须映射回证据对象。
- 校验器和评估器检查缺失引用、无证据支撑的章节以及来源覆盖程度。

一句话：

> 我没有直接相信模型回答，而是把报告引用绑定到真实证据，再用评估指标检查报告有没有脱离证据。

### 难点四：如何面对真实外部服务的不稳定

这里的 `provider` 是外部服务供应方。例如：

- DashScope 提供大语言模型、文本向量和重排模型。
- Tavily 提供互联网搜索。
- Qdrant 提供向量存储与相似度查询。

`Strict provider mode` 是“严格真实服务模式”：配置缺失或外部服务调用失败时，系统直接暴露错误，不悄悄切换到本地假数据或简化实现。`Fallback` 则是失败后的备用方案。

真实问题：

- `.env` 文件开头的 BOM（Byte Order Mark，字节顺序标记）隐藏字符导致严格模式配置没有被正确读取。
- Celery 后台任务进程冷启动时，任务长时间停留在 `queued`（已排队）状态。
- 大语言模型的结构化输出把本应为列表的字段返回成 `null`（空值）。
- Tavily 搜索服务偶发 HTTP 400（请求格式或参数不被服务接受）错误。
- 在严格真实服务模式下，完整 PDF 的解析、向量化和入库耗时过长。

一句话：

> 接入真实 API 密钥后，难点从“功能能不能写”变成“如何处理外部服务的延迟、错误、返回格式漂移，以及如何通过运行记录定位问题”。

### 难点五：如何证明项目不是空架构

关键资产：

- 5 篇联邦学习论文组成的本地语料库。
- 3 条系统记忆。
- 2 次完整成功的研究运行。
- 每次运行保存报告、运行轨迹和质量评估 JSON 文件。
- MCP 工具工作台的 10 项就绪检查全部通过。
- 严格真实服务模式已就绪。

一句话：

> 我用真实实验产物证明整条链路确实运行过，而不是只在 README 说明文档里画架构。

## 3. 哪些功能值得讲，哪些不要展开

先解释三个容易混淆的词：

## 5. 系统分层

你可以先把项目理解成 4 个主执行层：接口层、工作流层、智能体决策层、证据检索层。系统记忆、质量评估和运行轨迹不是孤立的一层，而是贯穿这 4 层的保障能力，第 6、7 节会单独解释。

### 第一层：产品/API 层

`FastAPI` 是 Python 的 Web 接口框架，用来把项目能力通过 HTTP 网络接口提供出去。`Celery` 是后台任务队列，用于执行耗时研究任务；`Redis` 保存队列消息和部分任务状态。

核心文件：

- `server.py`
- `pipeline.py`
- `celery_app.py`

职责：

- 接收研究任务。
- 提供文档、记忆、运行结果、运行轨迹、质量评估和运行配置查询接口。
- 在严格真实服务模式下，让接口服务与后台任务进程分开运行。

为什么合理：

- 真实模型调用、联网搜索、文本向量化和重排都可能较慢，不能让前端页面一直同步等待。
- 任务状态、最终结果和运行轨迹分别保存，面试时可以证明系统不只是“输入问题后吐出一个答案”。

能讲的点：

> FastAPI 不是为了堆后端框架，而是为了把研究过程暴露成可检查的接口：提交任务、查询状态、读取结果、查看运行轨迹、质量评估、系统记忆和资料库状态。

### 第二层：LangGraph 工作流层

`LangGraph` 可以理解成“带状态的流程图框架”。图中的每个节点完成一个明确步骤，节点之间传递同一个任务状态；程序可以根据状态决定走哪条分支、是否循环、是否修订。

核心文件：

- `graph_runtime.py`
- `pipeline.py`

节点大致是：

```text
初始化研究任务
-> 读取相关记忆
-> 拆分研究计划
-> 决定工具和证据要求
-> 执行一个或多个研究子任务
-> 生成报告
-> 校验引用并评估质量
-> 必要时准备修订
-> 写入有价值的记忆
-> 保存结果并结束
```

为什么用 LangGraph：

- 这个流程需要保存状态，也存在条件分支、修订循环、检查点和运行回放。
- 如果写成一条从头到尾的普通调用链，就很难看清每一步为什么发生，也不方便定位失败。

能讲的点：

> LangGraph 的价值不是增加一个流行框架名，而是把复杂研究过程拆成明确状态：规划、检索、搜索、报告、校验、评估和记忆写入。每一步都能在运行轨迹里看到。

### 第三层：Agent 决策层

这里的“多个 Agent”不是同时放出多个会自由聊天的机器人，而是让大语言模型在不同步骤承担不同职责，并限制每个角色可以读取的状态、输出格式和可调用工具。

核心文件：

- `agents/planner.py`
- `agents/supervisor.py`
- `agents/researcher.py`
- `agents/reporter.py`
- `agents/verifier.py`
- `schemas.py`

关键概念：

- `Planner`：规划器，把复杂问题拆成多个计划项。
- `ResearchSupervisor`：研究监督器，决定使用哪些工具、如何改写查询以及证据需要达到什么条件。
- `Researcher`：研究执行器，执行搜索、网页阅读、本地文档检索和 MCP 工具调用。
- `Reporter`：报告生成器，基于已有证据合成报告。
- `Verifier/Evaluator`：检查引用、覆盖率、证据充分性。

你要理解的不是“多个智能体听起来很厉害”，而是：

> 每个智能体角色的职责边界不同。规划器负责拆问题，研究监督器负责选择工具和研究方向，研究执行器负责收集证据，报告生成器负责写报告，校验器和评估器负责质量门控。

面试追问“多 agent 是不是噱头”时：

> 不是所有问题都需要多个智能体。只有当问题能拆成多个相对独立的研究方向时，研究监督器才会发出多个 `ConductResearch` 研究指令。每个研究执行器都有最大迭代次数，避免无限搜索和成本失控。

### 第四层：证据与 RAG 检索层

这一层回答的是：“系统从哪里找到资料，怎样把资料变成报告可以使用的证据？”

核心文件：

- `document_reader.py`
- `retrieval/store.py`
- `retrieval/fulltext.py`
- `retrieval/rerank.py`
- `source_reader.py`
- `search.py`

这层是项目最值得学的部分。

本地文档的 RAG 链路：

```text
文件或人工录入的文本
-> 文档读取器解析纯文本、Markdown、HTML 或 PDF
-> 保留文档、章节、页码等结构
-> 按段落切成用于精确检索的小片段
-> 为小片段补充所属文档和章节背景
-> 写入 Qdrant 语义向量索引
-> 写入 SQLite FTS5/BM25 关键词索引
-> 根据实体关系补充候选片段
-> 合并三路检索候选
-> 使用重排模型重新排序
-> 补回命中片段的父段落和相邻内容
-> 生成带来源信息的可引用证据
```

为什么不只做简单向量检索：

- 文本向量擅长找语义相似内容，但可能漏掉论文名、缩写、指标和系统组件名。
- BM25 关键词检索可以补充专有名词和精确术语命中。
- 重排模型可以结合完整问题，更精细地比较多路召回的候选证据。
- 父段落和相邻片段扩展可以避免只给模型一个脱离上下文的小片段。

你要重点掌握 5 个词：

- `Dense retrieval`：语义召回，找“意思相近”的文本。
- `BM25`：关键词召回，找“词语精确匹配”的文本。
- `Fusion`：候选融合，把语义、关键词和图关系三路结果合并。
- `Rerank`：重排，根据当前问题重新判断哪些候选最相关。
- `Parent/neighbor context expansion`：上下文扩展，命中小片段后补回父段落和相邻内容。

受 LightRAG 启发的轻量图关系信号怎么讲：

> 这里不是完整的 GraphRAG 或 LightRAG 系统，而是一个轻量图关系增强信号。系统从文本片段的标题、来源和正文中识别实体，记录“片段包含哪些实体”以及“哪些实体经常共同出现”。查询命中某个实体时，系统会把与该实体及其相邻实体相关的片段加入候选，再交给重排模型排序。

这里的“实体”可以是论文名、算法名、框架名或系统组件名。例如查询 `FedRolex` 时，图关系可能补充与“模型异质性”共同出现的其他片段。

这部分不要夸大，但要会讲它解决什么：

> 它用来补充短实体名、系统组件名和跨片段关系的召回，不是用来构建企业级知识图谱。

外部搜索和来源阅读链路：

```text
Tavily 联网搜索
-> 返回搜索摘要和网页正文
-> 提取相关段落，或切分、重排后再压缩
-> 生成带标题、网址和正文的可引用证据
```

为什么需要来源阅读器：

> 搜索摘要太短，直接把整页网页正文交给模型又贵又乱。因此中间需要一个来源阅读器，把网页正文压缩成与当前问题相关、可以引用、可以追溯的证据。

## 6. 系统记忆怎么理解

核心文件：

- `memory/store.py`
- `pipeline.py`

项目里的系统记忆（Memory）不是把全部聊天历史直接拼进提示词（Prompt）。提示词是发送给大语言模型的输入说明，内容过长会增加成本并引入无关信息。

它分三类：

- `Session`：会话记忆，只对当前一次运行或会话有用，例如本轮研究的临时上下文。
- `Summary`：总结记忆，保存项目或主题的阶段性结论。
- `Canonical`：规范记忆，保存相对稳定、以后可以重复使用的事实或偏好。

记忆治理（Governance）是指决定“什么可以长期保存、发生冲突时怎么办”：

- 规范记忆不应该被一次临时输出随便覆盖。
- 如果新旧事实冲突，系统标记 `needs_review`（需要人工或后续流程复核）。
- 召回记忆时综合考虑关键词匹配、向量语义相似度、置信度和记忆层级权重。

举例：

> “用户这一次想比较 FedAvg 和 pFedMe”适合作为会话记忆；“当前研究主题聚焦联邦学习异质性”适合作为总结记忆；“项目默认使用 Qdrant 作为向量数据库”才可能作为规范记忆。三者不能混在一起保存。

面试说法：

> 我把记忆当成可治理的系统状态，而不是提示词中的超长聊天历史。系统区分会话记忆、主题总结和稳定事实，并保留置信度及冲突复核状态，避免模型把一次临时输出当成永久事实。

## 7. 质量评估和运行轨迹怎么理解

质量评估（Evaluation）回答“这次报告是否达到要求”，运行轨迹（Trace）回答“系统为什么得到这个结果”。

核心文件：

- `evaluation.py`
- `ledger.py`
- `telemetry.py`
- `storage.py`

当前质量评估不是大规模公开基准测试（Benchmark），而是一次任务完成后的自动质量检查，目的是让失败原因可见。

指标包括：

| 指标字段 | 中文含义 | 主要检查的问题 |
| --- | --- | --- |
| `plan_coverage` | 计划覆盖率 | 研究计划中的任务是否都得到回答 |
| `evidence_sufficiency` | 证据充分性 | 每个结论是否有足够证据 |
| `tool_selection_coverage` | 工具选择覆盖 | 计划要求使用的工具是否真的被调用 |
| `query_rewrite_count` | 查询改写次数 | 系统是否根据证据缺口调整过查询 |
| `source_quality_score` | 来源质量分 | 证据来源是否足够可靠 |
| `context_precision` | 上下文精确度 | 取回的证据中有多少真正与问题相关 |
| `context_recall` | 上下文召回度 | 回答所需的重要证据是否被找全 |
| `faithfulness_proxy` | 忠实度代理分 | 报告内容是否与所引证据一致 |
| `citation_precision` | 引用准确率 | 报告中的引用是否能映射到真实证据 |
| `citation_source_coverage` | 引用来源覆盖率 | 报告是否使用了足够多且合适的来源 |
| `unsupported_sections` | 无证据章节 | 哪些章节缺少引用或证据支持 |

你不需要把公式全背下来，但要懂每个指标想抓什么问题：

- 没按研究计划回答：计划覆盖率低。
- 证据数量或内容不足：证据充分性低。
- 报告引用无法映射到证据：引用准确率低。
- 来源种类太少或使用不充分：引用来源覆盖率低。
- 报告表述和证据不一致：上下文精确度或忠实度代理分低。
- 有些章节没有引用：无证据章节列表不为空。

运行轨迹通常记录：

- 当前执行到哪个工作流节点。
- 大模型做了什么结构化决策。
- 调用了哪个工具，输入和返回摘要是什么。
- 新增了多少证据，来自多少个不同来源。
- 为什么继续研究、停止研究或触发修订。
- 外部服务是否超时、报错或返回异常格式。

面试说法：

> 我没有假设模型输出一定可信，而是在运行后用一组自动指标近似检查计划覆盖、证据充分性、引用覆盖、来源质量和无证据章节。失败的运行也会保留下来，因此可以通过运行轨迹复盘系统为什么拒绝或标记一个报告。

## 10. 高频追问答案

### 问：这个项目早期主要由 AI 辅助生成，也就是常说的 vibe coding，你自己真懂吗？

答：

> 项目早期确实借助 AI 工具快速搭建，这种以自然语言驱动 AI 生成代码的方式通常被称为 vibe coding。但后面我按工程链路重新做了复盘和实验：明确产品定位，梳理 LangGraph 工作流、智能体式 RAG、系统记忆、运行轨迹和质量评估的边界，并在严格真实服务模式下跑通完整实验。过程中还修复了 `.env` 隐藏字符、Celery 任务状态可观测性、大语言模型结构化字段返回空值等真实集成问题。所以现在我讲的是系统设计、运行证据和问题复盘，不是只展示 AI 生成的代码。

### 问：为什么不用简单 RAG？

答：

> 简单 RAG 通常是“输入问题、取相似度最高的几个文本片段、直接回答”，适合常见问题问答，但不适合复杂研究。复杂研究还需要拆问题、决定使用互联网还是本地资料、阅读网页正文、校验证据、生成引用报告，并在证据不足时修订。因此我把 RAG 作为证据获取能力，主流程使用 LangGraph 编排。

### 问：为什么要同时使用 Qdrant、BM25 和重排模型？

答：

> Qdrant 语义向量检索负责寻找意思相近的内容，但可能漏掉论文名、指标、缩写和系统组件名。BM25 保留精确关键词信号。两路结果合并后，再用重排模型结合完整问题重新排序。这个组合比只取向量相似度最高的几个片段更适合研究报告。

### 问：MCP 有什么实际用？

答：

> MCP 在这里不是企业网关，而是统一的工具注册和调用协议。本地工具工作台提供四个默认工具：`search_grounding_corpus` 检索本地证据库，`recall_project_memory` 读取项目记忆，`inspect_research_runs` 检查历史运行和评估结果，`check_demo_readiness` 检查实验所需服务和数据是否就绪。研究执行器可以用统一格式调用这些能力，实验前也能自动检查链路是否完整。

### 问：受 LightRAG 启发的图关系检索是不是噱头？

答：

> 我不会把它讲成完整 LightRAG。它只是轻量实体共现关系，用来补充语义检索和 BM25 对短实体、组件名、跨片段关系不敏感的问题。命中结果会保存图关系分数、查询实体和匹配实体等元数据，因此可以检查它是否真正贡献了候选结果，而不是黑盒卖点。

### 问：实验演示够真实吗？

答：

> 当前实验不是大规模生产资料库，但已经不是空壳。它有 5 篇论文组成的资料库、3 条系统记忆、2 次完整成功运行，以及对应的报告、运行轨迹和质量评估文件。运行时真实调用大语言模型、文本向量、重排、联网搜索、Qdrant、Celery、Redis 和 MCP 工具工作台。作为秋招项目实验已经足够，边界是规模受控的论文摘录资料库，不是生产知识库。

## 11. 你最终要背熟的 30 秒版本

> AI Research Copilot 是一个面向复杂问题的人工智能研究助手。它使用 LangGraph 把一次研究拆成规划、研究监督、资料搜索与阅读、本地 RAG 检索、报告生成、引用校验、质量评估和记忆写入。RAG 层同时使用 Qdrant 语义向量检索、SQLite BM25 关键词检索、轻量实体关系补充、Qwen 重排和上下文扩展。外部搜索得到的网页正文会被压缩成带来源的证据，最终报告只能引用这些已有证据。为了证明系统不是空架构，我在严格真实服务模式下跑通了两个完整实验，并保存论文资料库、系统记忆、报告、运行轨迹和质量评估文件，同时修复了配置隐藏字符、后台任务状态和模型结构化输出异常等真实问题。

| `Fusion` | 候选融合 | 合并多路检索结果 |
| `Rerank` | 重排 | 对候选结果进行更精细的二次排序 |
| `Top-k` | 取分数最高的前 k 个结果 | 例如取最相似的前 5 个片段 |
| `Grounding` | 证据依据约束 | 要求回答建立在真实资料上 |
| `Evidence` | 证据对象 | 正文片段加来源、标题、网址等信息 |
| `Citation` | 引用 | 报告结论指向具体证据 |
| `Faithfulness` | 忠实度 | 报告是否忠于所引用证据 |
| `Memory` | 系统记忆 | 跨步骤或跨任务保存有价值信息 |
| `Trace` | 运行轨迹 | 记录每一步决策、工具调用和结果 |
| `Checkpoint` | 检查点 | 工作流关键步骤保存的状态快照 |
| `Replay` | 回放 | 根据轨迹和检查点复盘一次运行 |
| `Evaluation` | 质量评估 | 检查计划、证据、来源和引用质量 |
| `Proxy metric` | 代理指标 | 用自动规则近似判断难以直接衡量的质量 |
| `Artifact` | 运行产物 | 报告、轨迹、评估等实验文件 |
| `Run` | 一次完整运行 | 从输入问题到生成并评估报告 |
| `Worker` | 后台任务进程 | 从队列中取出并执行耗时任务 |
| `Queued` | 已排队 | 任务已提交，但后台进程尚未执行 |
| `JSON` | 结构化文本数据格式 | 项目用它保存轨迹和评估结果 |
| `Benchmark` | 基准测试 | 用统一任务集合比较系统效果 |
| `OCR` | 光学字符识别 | 从扫描图片或扫描 PDF 中识别文字 |
| `Observability` | 可观测性 | 通过日志、状态和轨迹了解系统内部发生了什么 |

## 15. 第一次读代码的固定方法

你不需要一开始就理解 Python 的每个语法细节。每打开一个核心文件，按下面顺序做标记：

1. 找入口函数：一次任务最先进入哪个函数。
2. 找输入：这个函数拿到的是问题、计划、证据还是运行状态。
3. 找主要调用：它接下来调用规划器、检索器、模型还是数据库。
4. 找输出：它返回计划、证据、报告还是评估结果。
5. 找失败处理：异常会重试、回退、标记失败还是写入运行轨迹。

建议在纸上画四列：

| 输入 | 当前步骤 | 输出 | 失败时怎么办 |
| --- | --- | --- | --- |
| 用户问题 | 规划器拆解 | 研究计划 | 计划为空则修复或失败 |
| 研究计划 | 研究执行器检索 | 证据集合 | 证据不足则继续搜索 |
| 证据集合 | 报告生成器写作 | 引用报告 | 引用不合法则校验失败 |
| 报告与证据 | 评估器检查 | 通过或修订 | 记录失败原因并触发修订 |

当你能给核心文件填完这四列时，就已经从“完全没看过代码”进入“能顺着主链路读代码”的阶段。
